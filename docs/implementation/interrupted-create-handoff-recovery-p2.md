## Semantics and evidence limits

- [Fence acquisition](../../src/core/task-persistence/parentHandoffFence.ts:65) uses exclusive directory creation per parent. Two instances sharing a temporary filesystem cannot both acquire the same held fence in the tested cooperative case. Clean release permits the next persisted generation. A held/abandoned lock is not automatically stolen.
- [Ownership validation and release](../../src/core/task-persistence/parentHandoffFence.ts:113) reject the old token after a test replaces the fence. This does **not** prove atomic enforcement at a task/API write or child-start boundary. There is no transaction wrapper that enforces outer-before-inner lock ordering.
- [Eligibility evaluation](../../src/core/task-persistence/interruptedCreateHandoffEligibility.ts:95) checks supplied interrupted status, action kind/ID, root/parent identifiers, question/awaited-child absence, owner certainty, completeness flags, child attribution and raw call/result history. An ambiguous directory with missing metadata blocks evaluation; a matching success or uncorrelated error blocks progression.
- The evaluator is **not an authoritative reader**. Inventory completeness, absence of live owner, child attribution and error correlation are supplied assertions, not facts it discovers or durably verifies. The superseded-action test changes supplied evidence; it is not a real provider/store stale-cache test.
- The parent/root/earlier-child fixture is in memory. The transient directory is represented as evidence, not created/scanned on disk. Only the fence tests use temporary files. No persisted parent/root/child fixture, real multi-process host, process kill, power-loss simulation or recovery commit is covered.
- Source branches for lineage, question priority, extra/orphan calls and missing readers are not all covered by the fourteen tests. Presence of a check in source is not a passing negative-case test. The earlier completion narrative overstated this coverage; this report narrows the claim.

### Known scaffold hardening tasks before any runtime wiring

These are bounded source-review observations, not newly demonstrated test failures or implemented fixes:

1. Fence writes sync file contents but do not sync parent directories. Filesystem support, storage-path canonicalization, symlink/permission safety and fail-closed generation parsing/overflow need proof. An empty generation file currently parses numerically as zero.
2. Owner read-back followed by recursive release is not atomic against external fence replacement. Failure cleanup also recursively removes a lock directory. Prove that a stale owner cannot remove a replacement owner's lock during these windows; the existing replacement test does not cover the intervening race.
3. Ownership read-back checks the owner record, not an atomic generation guard inside each existing writer. Unsupported/legacy peer writers must block recovery, not rely on a Boolean completeness flag.
4. Eligibility needs validated disk evidence and complete parent-chain/root/child registry linkage, including every parent child ID, persisted handoff intent and transient attribution. Caller-supplied labels cannot constitute production proof.
5. Tool-boundary inspection scans supplied raw history without proving message roles, ordering, duplicate IDs, malformed block handling or provider-effective condense/truncation history.
