## Candidate semantics and limits

The storage port must supply the outer parent fence, fresh authoritative discriminator/question priority, immutable identity checks across parents/actions, one accepted owner per action, protected durable blob writes and authoritative disk read-back. There is deliberately **no** default adapter. The scaffold does not claim, remove or edit queue items, advance the journal beyond intake, append API turns, repair metadata or start a loop.

The candidate digest covers canonical binding, stable ID, origin, ordering timestamp and exact text/images. This explicitly detects same-ID ownership or payload changes; its naming/serialization must be agreed in P1 review before wiring. The helper permits only canonical base64 PNG/JPEG/GIF/WebP; unresolved URIs or unsupported formats fail closed. Bounds: 1 MiB UTF-8 text, 8 MiB combined decoded images, 10 images, 16 MiB serialized request. No truncation. Actual image-content validation/resolver lifetime remains a production adapter task.

The fixture stores inline data only in a disposable test file; it does **not** implement the proposed blob schema, fsync/rename durability, symlink/permission safety, cross-host locking, fencing generations or crash-kill tests. Recreating a fixture/client proves disk-backed retry behavior, not power-loss or real extension/webview restart durability. Webview pending-snapshot persistence, receipt transport and draft revision ownership are caller responsibilities not yet wired.
