## Proposed write-time identity and reconciliation (provider owner to decide)

**B1 fingerprint proposal, not an existing schema:** canonical root + parent ID + exact old `create_subtask` action fields (ID, kind, mode, message, todos, approvalText) + terminal assistant `new_task` call ID/name/input and its effective message position + operation kind/version `manual_supersede_B1` + fixed text _“operator superseded this handoff; earlier child outcome unknown; this resolution did not start a child”_. Compute a deterministic digest of canonical serialized identity; place an approved unambiguous versioned marker/digest in the **single user-role `tool_result`**, `tool_use_id=old action ID`, `is_error=true`, fixed content. Define and test exact encoding, duplicate detection, root binding, and marker parsing with provider owner; same ID and `is_error` without the marker is **conflict**, never already-done. Before append under API-file lock compare full _raw and effective_ ordered history: one unique terminal matching call, no unresolved sibling/orphan/old result/later action or turn, and exact full saved action, status, owner, question and root still matching under exclusion. Persist exactly one result, no message/queue/model/child effects. [Effective projection](../../src/core/condense/index.ts:546) can discard pre-summary calls/results; [prepareUserMessage](../../src/core/task/apiConversationHistory.ts:111) converts a result to text if the last effective turn is not assistant, while [validator](../../src/core/task/validateToolResultIds.ts:87) can deduplicate/remap/inject tool results. Therefore the raw terminal call must also be terminal/visible in actual effective history; no summary/truncation or provider-specific normalization may silently change this pair. Provider-specific wire serialization remains UNKNOWN. The proposed B1 writer must not use generic message preparation, and the owner must confirm that direct persisted shape remains the effective shape.

After **success or any error**, including rename followed by exception ([commit point](../../src/utils/safeWriteJson.ts:140)), strict reread under same exclusion: exactly one approved marker/digest/result with identical history boundary => B1 committed/already-done; no result and unchanged prerequisites => only a _new conditional_ attempt after renewed confirmation; unreadable API, conflicting/later result or changed owner => UNKNOWN/BLOCKED, no blind retry. A failed first read-back remains UNKNOWN until independently successful reread/restart; never interpret thrown save as no commit. The [ordinary retry](../../src/core/task/Task.ts:1431) is not suitable. No claim of fsync/power-loss durability.

**B2:** after one authoritative B1 result, hold exclusion and reread result and metadata; under the task-file lock require identical canonical root/parent, full still-owned old action, `interrupted` status, no pending question/awaited/delegated/matching child, no newer API turn and unchanged relevant lineage. Recheck API and task state after write before ready. Crash after API commit but before task write or failed task write => restart _repair only_, never B1 append, request, queued claim or automatic child. Task commit-then-error => strict reread of both files: exact repaired pair => already-done; exact old metadata + B1 result => repair-only conditional retry; partial action/status change, unknown read or conflict => BLOCKED. Gate [generic hydration clear](../../src/core/task/Task.ts:2675) for B marker before question handling; metadata already repaired + exact result => already-done without writing. No ready feedback until both authoritative reads match and equivalent queued item has been resolved by ordinary controls. Child ownership/question/new action always blocks or routes to its ordinary handler.
