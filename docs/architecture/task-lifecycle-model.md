# Task lifecycle model-check suite

Zoo Code checks task lifecycle protocols through one umbrella command for independent bounded checks. Run the complete suite locally with:

```sh
pnpm lifecycle:model-check
```

The baseline command runs seven independent bounded checks in sequence:

1. the persisted task delegation lifecycle;
2. shared-store concurrency across task-history hosts;
3. production-backed handoff reducers with an abstract provider/scheduler protocol;
4. the task cleanup protocol;
5. request-stream parser scoping;
6. completion persistence; and
7. delegated-mode reader refinement.

The planned two-sibling fan-out protocol is intentionally outside the baseline and CI umbrella. Run it explicitly with `pnpm fanout-protocol:model-check`; it describes optional future functionality, not current production coverage.

This umbrella command is the single model-check entry point in the `compile` CI job after type checking. Command-level composition does not merge the submodels' state spaces: each checker retains its own bounds, transitions, invariant ownership, reachability requirements, and counterexample format. In particular, parser state is not part of the persisted lifecycle graph. The focused parser checker remains directly runnable with `pnpm parser-scope:model-check` for debugging.

An individual checker fails if it finds an invariant violation, a modeled action becomes unreachable, a named semantic landmark disappears, or exploration exceeds its declared state budget. A lifecycle violation includes the shortest breadth-first event trace, every intermediate state, and the active bounds so the sequence can be replayed as a focused regression test.

A checker printing `passed` means only that its configured bounded invariants, expected witnesses, reachability requirements, and state budget succeeded. It does not close a linked issue, prove arbitrary-task correctness, or establish refinement for production consumers that the checker does not execute.

Executable cross-model composition should be added only when a correctness claim genuinely spans two or more submodels and there is an explicit, production-grounded boundary mapping between their events or state. That composition must state a bounded joint exploration strategy and own cross-model invariants that cannot be proved within either child model alone. Shared command orchestration or conceptual adjacency is not sufficient reason to multiply independent state spaces.

## Why an executable TypeScript model

The models use small explicit-state explorers rather than adding Quint, TLA+/TLC, or Alloy. This is deliberate:

- Zoo's current risks are finite safety properties over a small persisted state machine, not yet temporal liveness or fairness properties.
- The delegation and shared-store explorers call production transition functions from `src/core/task-persistence`. `ClineProvider` uses those same functions inside serialized and atomic store operations, reducing specification drift for those protocols.
- Breadth-first exploration gives a deterministic, shortest-by-event counterexample with no Java or separate specification toolchain.
- Bounds and budget exhaustion are explicit. CI never reports a truncated exploration as a pass.

This follows the same initial-state, next-state, reachable-state, invariant structure described by the [TLA+ high-level view](https://lamport.azurewebsites.net/tla/high-level-view.html) and [Quint's model-checker documentation](https://quint-lang.org/docs/model-checkers). The implementation connection is important: Quint's [model-based testing guidance](https://quint-lang.org/docs/model-based-testing) notes that checking a specification alone does not show that production code implements it.

TLA+/PlusCal or Quint with TLC becomes a better fit when the lifecycle needs temporal properties, fairness assumptions, unbounded queues, or refinement between protocol layers. Alloy is better suited if relational ownership structure becomes harder than event ordering; Alloy analyses are explicitly bounded by scope, as described in the [Alloy tutorial](https://alloytools.org/tutorials/online/maintext-FS-1.html). Randomized model-based testing can complement, but not replace, the exhaustive bounded check when a production adapter is available; [fast-check documents command models](https://fast-check.dev/docs/advanced/model-based-testing/) and [controlled Promise scheduling](https://fast-check.dev/docs/advanced/race-conditions/). Jepsen-style history checking remains useful for distributed persistence behavior, but is heavier than this in-process lifecycle protocol; see Jepsen's [consistency model overview](https://jepsen.io/consistency).

## Production mapping

| Model concept             | Production concept                                                                                                                                                                 |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Task record and status    | `HistoryItem` persisted by `TaskHistoryStore`                                                                                                                                      |
| `delegate(parent, child)` | `ClineProvider.delegateParentAndOpenChild`                                                                                                                                         |
| `interrupt(child)`        | cancellation or eviction through `markDelegatedChildInterrupted`                                                                                                                   |
| `complete(child)`         | `ClineProvider.reopenParentFromDelegation`                                                                                                                                         |
| `abandon(child)`          | `ClineProvider.abandonSubtask`                                                                                                                                                     |
| `resume(task)`            | `Task.restoreLiveStatusOnResume` → `ClineProvider.resumeInterruptedTask` → `TaskHistoryStore.resumeInterruptedTask`, where a resumed loop starts, under a bounded parent-lock wait |
| Atomic event step         | `atomicReadAndUpdate`, `atomicUpdatePair`, `resumeInterruptedTask`, and per-parent delegation transition lock                                                                      |
| Event interleaving        | Competing completion, cancellation, abandonment, resume, and new delegation calls                                                                                                  |

The model has three fixed task slots, enough to cover competing siblings and a nested parent-child-grandchild chain. It explores every reachable interleaving through depth 12, deduplicating canonical states. Representative checks also exercise rejected operations that do not create a new state: a second concurrent delegation while the first child is active, stale completion after re-delegation, late completion after abandonment, completion after interruption, and nested completion. Named semantic landmarks require the graph to retain interrupted-child re-delegation and nested delegation even when the raw state total changes.

`resume(task)` uses the production `resumeInterruptedTask` reducer. It moves `interrupted → active` only when the parent (`delegated` or `blocked_protocol_error`) still awaits that task, or when the task has no parent link (never delegated, or abandoned). The model offers `resume` for every interrupted task and adds no guard of its own, so an unguarded reducer produces a linked active child its parent does not await and fails the awaited-child invariant. The `interrupted-child-resume-then-delegation` landmark requires `interrupt(x)`, then `resume(x)`, then an enabled `delegate(x, …)`. It is evaluated on explored transitions because the resumed state equals an already-visited state and is deduplicated. `interrupted → active` remains absent from `VALID_TASK_STATUS_TRANSITIONS`, which keeps stale ordinary saves from undoing an interruption (#560). `TaskHistoryStore.resumeInterruptedTask` is the only write that bypasses that table, and only for this reducer's result. Its production callers are the resume paths in `Task` that start a loop: the generic Resume or typed answer, the restored pending-action denial and its `completion_result` fallback, the pending-question continuation, and the interrupted create-handoff recovery after its durable result and action clear. Showing the Resume ask on an opened chat does not call it. One opening path does: when the pending question was already answered and that answer is durably saved, opening the chat continues it without a click (pre-existing behavior), and that continuation restores `active` before its loop starts. The restore waits at most `resumeDelegationLockWaitMs` (5 s) for the parent's delegation lock. On expiry it writes nothing, the task stays `interrupted`, and the resume proceeds as it did before this restore existed.

Production completion also accepts a recovery-compatible `active` parent that still awaits the returning child, then clears the stale pointers. Normal model transitions never create that intermediate state, so it is covered by a focused reducer test rather than admitted as a generally valid reachable state.

## Shared-store concurrency model

The same umbrella command runs the historical shared-store explorer over two hosts, importing production delta/merge functions rather than assuming coherent caches or transactional pair writes. These six scenarios intentionally describe the old protocol **without** the current ordinary-instance authority guard:

- each host has an independent cache and host-local mutex;
- store read/update operations hold the host mutex, while live-task snapshots used by completion and message saves may outlive it;
- a write delta is computed relative to that host's cache;
- revalidation under the per-file disk lock checks only status-transition legality;
- fields absent from the delta preserve the current disk value, `childIds` are unioned, and other same-field conflicts are last-writer-wins;
- `atomicUpdatePair` commits its files in order, with another host able to act between file commits;
- successful pair-operation cache entries publish together after both file writes; if the second write fails, the cache publishes only the first committed record;
- cache refresh is explicit and may occur after an external live-task snapshot was captured.

The historical explorer does not invent a record version or compare-and-swap token for that old protocol. It checks host-mutex and file-lock ownership, whole-file delta rejection, disk-field preservation, child-history union, and pair write order in every state reachable within its six bounded scenarios. Those scenarios include distinct-task writes from #920 and a second-write pair failure, and all seven phases (`read`, `prepare`, `revalidate`, `commit`, `refresh`, `reject`, and `fail`) must remain reachable without exceeding the state/depth budgets. Positive semantic landmarks additionally require a stale cache beside newer disk state, the first pair write committed while the second is pending, and the same committed prefix retained after the second write fails.

Two desired properties are false in the historical protocol and remain exact issue-keyed shortest-witness ratchets, not silently allowed assertion failures:

- [#1469](https://github.com/Zoo-Code-Org/Zoo-Code/issues/1469): an old completion can commit after a newer handoff and clear it because disk revalidation checks status legality, not exact-child ownership.
- [#1021](https://github.com/Zoo-Code-Org/Zoo-Code/issues/1021): after abandonment and cache refresh, a stale live-task save can preserve the new interrupted status while restoring old lineage fields.

CI fails if either exact historical causal witness or violation class changes, a historical witness disappears, a named semantic landmark or modeled phase becomes unreachable, a new safety violation appears, or exploration truncates. Raw reachable-state totals are printed as diagnostics, not used as ratchets: harmless representation changes can alter them without weakening protocol coverage.

The known-unsafe witnesses currently compare exact shortest action sequences. This is intentionally simple and reviewable, but brittle to harmless action renames or serialization refactors. A causal partial-order comparator would reduce that brittleness but would add a second trace-equivalence protocol to maintain. Until that complexity is justified, update an exact witness only after confirming the terminal violation class and required causal ordering are unchanged.

`TaskHistoryStore.realConcurrency.spec.ts` complements the abstract interleavings with one synchronized integration smoke check through the real `proper-lockfile` and filesystem rename path; broader VS Code E2E remains reserved for restart and extension-host behavior.

### Exhaustive bounded invariants

Every reachable current-protocol state checks:

1. Captured identity stays equal to the original snapshot, despite cache refresh and lease generation changes.
2. Every ordinary save commit has matching authoritative ID/revision/parent/root and an acceptable explicit snapshot at publication. **An old snapshot cannot commit after its disk authority advances.**
3. Detached child lineage is monotonic: no later ordinary metadata save restores parent or root IDs.
4. Both abandonment revisions advance in child-first/parent-second file order; this is not atomic pair durability.
5. Typed refusal (stale revision/lineage, ownership loss, filesystem fence refusal, unrecoverable lock) is sticky for the same instance and permits no metadata commit, including bounded later attempts after detachment and cache refresh. Contention refusal (a bounded fence wait that expires while acquiring, because another owner holds part of the scope) refuses only that attempt: it publishes nothing and is not sticky, so a later save by the same instance, with the same captured authority, may still commit. The check is evaluated on outcomes in every phase: a sticky refusal never carries the contention reason, and no commit belongs to the attempt that contention refused.
6. Ancestry exclusion precedes host mutex/file ownership and remains held through the modeled effect.
7. Delta-absent disk fields survive; a failed save publishes no metadata, and failed second-file abandonment retains the committed child prefix in disk/cache.

The explorer has eight scenarios: child instance, parent instance, explicit metadata snapshot, and fresh rehydrated child, each with legacy-unset and revision-bearing initial authority. There are three task slots (parent, child, unrelated peer), two independent host caches/mutexes, one save per instance, one abandonment pair, one unrelated save, and bounded rejected late attempts. Every enabled ordering is explored; no schedule is sampled or disabled to obtain a pass. Both explorers retain **depth 32 and 100,000 states per scenario**, and fail on budget exhaustion or an unseen successor at the depth frontier.

Required positive/negative landmarks are: old snapshot beside refreshed cache; old child refused after cache refresh and a fresh lease; old parent refused by revision alone; explicit stale snapshot refused at final publication; sticky refusal after a later refreshed-cache attempt; detached child prefix after parent-write failure; fresh rehydrated child progress; unrelated commit while the parent exclusion is held; matching old-instance progress before abandonment; save failure with no metadata publication; and contention refusal followed by a successful later save by the same instance, with no publication on the refused attempt. All 11 current phases must remain reachable: read, acquire, check, prepare, revalidate, commit, refresh, reject, fail, sticky rejection, and post-refresh rejection. Applicable actions are required in each scenario, including contention refusal in every scenario except the fresh rehydrated child (it reads only after abandonment releases its scope); all eleven landmarks are required across the current scenarios. The explorer allows one contention refusal per save to keep the graph bounded; it models no retry loop.

**Case 19 (production mapping).** [The ordinary boundary](../../src/core/task-persistence/targetPersistenceBoundary.ts) and `Task.withStartExclusion` classify a `ParentHandoffFenceUnavailableError` with reason `timeout` (also when wrapped through `originalError`) as contention only when it is raised while acquiring exclusion, before the effect starts. The error still reaches the caller and nothing is published, but the instance is not refused. A timeout that escapes a started effect stays sticky, because the effect may already have written (for example `ui_messages.json` before the history upsert). Reasons `unrecoverable` and `filesystem` are always sticky (see the deadline classification below).

The background usage drain logs a warning and skips a contended save; the usage stays in the in-memory `api_req_started` message. Exactly one deferred save follows after 1 s, with the normal bounded fence wait and no loop. It is skipped when a save that snapshotted the messages after the skip has persisted, or when the instance is aborted, disposed or refused. If it also hits contention or fails, it is logged and not rescheduled. **Token/cost metrics can therefore still be lost** when that retry fails, or when the instance ends (abort, dispose, parent disposal during delegation and reopening from disk, extension close) before the retry and no newer save persisted them.

The `taskHistoryItemUpdated` broadcasts are fire-and-log at five sites: `updateTaskHistory`, `markDelegatedChildInterrupted`, `delegateParentAndOpenChild`, `markDelegatedChildProtocolBlocked` and `reopenParentFromDelegation`. Only those posts no longer wait for a renderer acknowledgement under a fence or start exclusion. Known remaining waits under a fence or start exclusion, left for a separate follow-up:

- **Resolved, gap (a): restored-task user waits.** `resumeTaskFromHistory` no longer holds the task's (or, for a child, the parent's) start exclusion while a restored task waits for the user. This covers the pending-action approval, the finish-subtask `completion_result` fallback, the generic Resume Task ask and the interrupted-create recovery ask. Each runs in three phases. Present: under the exclusion, `prepareAsk` shows the ask and returns its wait. Wait: outside every scope. Resolve: under a NEW `withStartExclusion(…, fresh = true)`, a bounded wait, because the answer's own un-awaited save may hold the lease. Before any effect, the resolve phase returns quietly if the instance was aborted or abandoned. It refuses with `OrdinaryPersistenceAuthorityError("Pending action ownership changed")` if the answer no longer belongs to the shown ask (`lastMessageTs`), or if authoritative metadata shows a different pending action or a status moved to `interrupted` or `completed` from the status read under the presenting scope. The authority entry check refuses a refused or advanced-revision instance. The interrupted-create path keeps its unchanged read-back check. Any refusal releases a claimed queued message, and so does a scope that rejects on exit after presenting an ask whose wait never starts. If the fresh re-acquire fails with non-sticky contention, nothing is applied. Inside a new bounded scope, the pending-action approval and the `completion_result` fallback re-check the owner first (a moved owner refuses as above, typed and sticky, and the ask is not shown again). The generic and interrupted-create paths have no owner check at this point: a moved interrupted-create action is shown again and refused only after the next answer, by its unchanged read-back (an untyped, non-sticky error). Nothing is re-delivered automatically, and a NEW user action is required, but only when auto-approval does not apply. **Deliberate exception, chosen by the user:** under auto-approval (for example subtask approvals while `queueSubtaskApprovalAllowed`), the re-presented ask is auto-approved per standing consent. A cycle can then repeat while contention comes and goes. Each cycle costs at least one full fence wait (30 s) and at most one bounded wait per lease acquired in the resolve and re-present phases (about 4 × 30 s for a child, which acquires parent and child in each phase), plus one persisted row. The cycle ends on success, abort, a sticky refusal or a failed re-present acquisition. A queued answer takes priority over auto-approval only while it is queued, so a queued deny-with-feedback that meets contention is handed back to the input and the re-presented ask is then auto-approved: **the explicit denial becomes an approval.** The user accepted this consequence on 2026-10-10. The unapplied answer's text and images go back to the chat input (`setChatBoxMessage`). A non-durable queued answer (for example generic Resume Task) was removed from the queue at drain, before it was applied, and is restored like a typed answer. Without a launched webview, a durable-ack queued answer stays claimed (kept, not consumable); a typed or non-durable queued answer is lost. If the re-present acquisition itself fails, the run ends (fails closed): the content is already in the input, but no live ask remains, nothing is applied, a non-sticky contention leaves the instance unrefused, and new messages are queued unused until the task is reopened. ### Fence failure adapters and availability limits

[Disposable fence tests](../../src/core/task-persistence/__tests__/interruptedCreateHandoffP2.spec.ts) cover generation-read I/O refusal, generation temporary-write/rename failure, owner bootstrap rename failure after generation advancement, five malformed/exhausted generation cases, and release-removal failure. [The fence](../../src/core/task-persistence/parentHandoffFence.ts) now classifies those I/O/bootstrap failures as typed filesystem refusal with sanitized error codes. Ownership loss remains a separate error and is checked before removal. Tests require retained lock/generation/temporary bytes, zero-wait competitor refusal, and preserved ownership of an unrelated holder. The nine new cases first failed against unchanged source because errors escaped untyped; the initial immutable-module mock failure is fixture evidence, not a production reproduction.

No lock is stolen by age, abandoned lock is deleted, timeout is increased, or retry-until-success policy is added. Bootstrap may publish only generation or temporary owner evidence; failed release may leave a lock held. Explicit bounded refusal and retained uncertain evidence remain the rule, with one exception: **exited-owner takeover by process proof** (approved 2026-10-09 after a crashed extension host held startup admission and hid all task history). A second, user-chosen exception is a task-level retry, not a fence change: auto-approved re-presentation of restored-task asks on contention (see gap (a) in the [Case 19 waits list](#current-ordinary-persistence-authority-model--ordinary-persistence-1021-20261007)).

- **Record.** `owner.json` (still schema 1; readers ignore the new field) carries a `holder`: pid, hostname, platform, `/etc/machine-id` where readable and, on Linux, pid namespace. Boot id and process start time are recorded only when `/proc/self/stat` starts with this process's own pid (a trusted /proc view).
- **Proof.** A contender may take over only when the holder is provably gone _on this host_: same hostname and platform, same machine id when both sides recorded one, same Linux pid namespace, and `kill(pid, 0)` fails with `ESRCH`. `ESRCH` is sufficient even for a holder recorded in another boot: no process with that pid exists in this namespace. If the pid exists, only Linux evidence from the same boot and a trusted /proc view proves exit: a different `/proc/<pid>/stat` start time (pid reuse) or a zombie. `EPERM`, any other error, a legacy owner without `holder`, a partial or unreadable owner, another host/platform/machine id/namespace, a live pid from another boot or an untrusted /proc view, or a generation file other than `g`/`g+1` all refuse as before. Pid reuse can only make a dead owner look alive, which refuses.
- **Race safety.** Owner tokens are unique and a moved lock never returns to the lock path, so reading token T there pins that instance until someone renames it. Only the holder of the deepest _claim_ for T may rename it. A claim is a complete directory renamed onto `<key>.takeover-<digest(T)>`; at most one contender wins, and it is never partial or removed. A crashed claimant is superseded only by a nested claim named from its claim token, after the same proof. The claim holder re-reads T and the generation (`g` or `g+1`), writes `g+1`, and renames the lock to `<key>.lock.exited-<g>-<uuid>`. A contender that observed T before T was moved and a successor installed reads a different token and moves nothing, even when that successor's holder has also exited. No code path renames a directory back onto the lock path (see Release), so the "never returns" premise holds; an empty directory at the lock path is only ever a competitor's own fresh `mkdir`. The next acquisition bootstraps `g+2`, so a wrongly superseded old lease fails `assertOwned()`.
- **Liveness of a failed takeover.** Transient I/O after a claim is published is retried in-call (3 attempts). If it still fails, the claim is kept as resumable in this process and any later attempt here resumes it, accepting `g` or `g+1`. Other processes stay refused only while the claimant is alive and has not retried.
- **Release.** `release()` checks ownership, renames the lock to `<key>.lock.released-<uuid>`, and re-reads its own record there (bounded retry). Nothing is ever renamed back onto the lock path, because POSIX `rename` onto an _empty_ directory succeeds and could replace a competitor's freshly created lock; a released directory is therefore never reinstalled. If the moved directory has another token or no `owner.json` (a replacement or a competitor mid-bootstrap moved in the window between the check and the rename), it stays aside and ownership loss is reported. That holder then fails its next `assertOwned()`; a competitor mid-bootstrap fails its `owner.json` write because its directory is gone, and the lock path stays free (refusal, not a stranded lock). If the own record stays unreadable after the retries, or the delete fails (possibly after removing `owner.json`), the lock is still released: the directory stays aside as evidence and `release()` resolves with `{ cleanup: "retained", code, retainedName }` plus a warning log. This report is non-throwing and non-sticky, so callers that release in `finally` keep their own result or error.
- **Evidence.** Exited locks and claims are renamed or left in place, never deleted.
- **Deadline classification.** When a wait reaches its deadline with the lock still present, the error reason says whether waiting again can help. `timeout` (contention, non-sticky for ordinary persistence): the lock held a complete owner whose holder is not provably exited. That includes a complete owner on another host or machine: it may be alive and release, and refusing healthy instances for good because of a legitimate remote holder would be worse than repeated bounded waits. `unrecoverable` (sticky, diagnostic `LEGACY_OWNER`, `INCOMPLETE_OWNER`, `UNREADABLE_OWNER` or `EXITED_OWNER_REFUSED`): the same lock instance (directory identity and `owner.json` bytes) showed no usable owner for at least max(1 s, half the wait) up to the deadline. "No usable owner" means a legacy holderless owner, a missing, incomplete or unreadable `owner.json`, or a provably exited owner whose takeover was refused. The fence re-observes the lock on every retry; any change, such as a competitor finishing its bootstrap or a replaced directory, restarts the window, so a competitor briefly between `mkdir` and its owner write is not misclassified. Waits shorter than 1 s (including the zero-wait handoff and target paths) always report `timeout`. A live process that could not determine its own identity records no `holder` and is indistinguishable from a legacy owner; a waiter that outlasts the window then refuses its instance until reopen.
- **Assumptions and limits.** Hostname plus machine id (when both are readable) identifies one machine among processes sharing the storage. Cloned images can share a machine id and hosts without one rely on hostname alone. On non-Linux hosts the pid namespace is assumed shared. A legacy lock written before this change (no `holder`) still needs manual recovery; a full wait on it now reports `unrecoverable`, so the waiting instance is refused once instead of waiting 30 s on every save. A lock whose recorded pid is now in use by another process in a different boot stays refused. Takeover is attempted only on contention; no background recovery exists.
- **Degraded startup.** If startup admission is still refused, `TaskHistoryStore.initialize()` loads history through the write-free `reconcile({ forceRefresh: true })` scan and starts the read-only watcher and periodic scan. It skips intent replay, delegation repair and migration, and rejects with `TaskHistoryStartupDegradedError`. The provider shows a localized notification chosen by the refusal: a held or unrecoverable lock (`timeout` or `unrecoverable`) names the lock folder and says to move it aside only if no other Zoo Code window is open; `INVALID_GENERATION` names the generation file (and the lock folder left by the failed bootstrap); any other filesystem refusal names the fence folder and the error code. The text says history was loaded but startup repairs were skipped, because ordinary task saves continue. Only a refusal before admission degrades; a refusal inside admitted startup still fails. Ordinary task writes keep their existing per-task fences, as after any failed startup; with the cache loaded they also keep transition and delta checks. The only write a degraded store makes is its own host presence record (below), because it still runs tasks.
- **Host presence and active-child startup repair (2026-10-10).** Every `TaskHistoryStore` publishes `<storage>/.host-presence/<token>.json` with its fence holder identity at the start of `initialize()`, before it waits for admission. It removes the record on `dispose()`, and the process removes all of its records synchronously on `exit`, because the sidebar provider's store is never disposed at shutdown ([hostPresence.ts](../../src/core/task-persistence/hostPresence.ts)). Startup repair of a `delegated` parent awaiting a persisted-`active` child (child → `interrupted`, parent → `active`) runs only when every other record is provably exited, by the same proof as exited-owner takeover. Otherwise the pair is left unchanged with a warning, for a later startup. Any doubt counts as live: another machine or pid namespace, a missing holder, an unreadable or malformed record. Records of provably exited holders are removed; nothing is decided by age. A second store in the same process counts as a peer. This prevents a second extension host (an F5 queue host) on shared storage from detaching a running pair, which made the child's completion fail with `ownership_moved`, **only when every host on that storage runs a build with this change**: an older build publishes nothing and is invisible. While a pair is left unchanged, abandoning or re-delegating needs an `interrupted` child, so the user opens the child first. Limits: the other repair branches (missing or completed child, no `awaitingChildId`) and intent replay are not gated. A peer that gives up waiting for admission during a long repair pass and resumes the same child is not seen. A record left by a crash (or a killed extension host) whose exit cannot be proven blocks active-child repair, with only a log warning naming the record, until it is moved aside: for example another machine, a changed hostname, a new pid namespace or boot after a WSL or container restart, or a reused pid on non-Linux hosts. A store whose publication fails is invisible to peers, as before. [Real-disk tests](../../src/core/task-persistence/__tests__/TaskHistoryStore.hostPresence.spec.ts) cover a live peer store, no peer, a later startup after all peers are disposed, an exited peer, and unprovable peers.

[Takeover tests](../../src/core/task-persistence/__tests__/parentHandoffFence.exitedOwnerTakeover.spec.ts) use real child processes that exit or are killed while holding the lock, live-holder refusal, cross-process and in-process races, a paused stale observer with an exited successor, crashed and transiently failing claimants, release racing a replacement or a competitor mid-bootstrap, partial deletes, an empty competitor directory, and unreadable own records. [/proc-trust tests](../../src/core/task-persistence/__tests__/parentHandoffFence.procTrust.spec.ts) mock a foreign /proc view. [Deadline classification tests](../../src/core/task-persistence/__tests__/parentHandoffFence.unrecoverable.spec.ts) cover legacy, missing, truncated and tokenless owners, a live owner, a foreign-host owner, a competitor finishing its bootstrap during the wait, and a replaced incomplete lock. [Degraded-startup tests](../../src/core/task-persistence/__tests__/TaskHistoryStore.degradedStartup.spec.ts) cover byte-identical storage, a real admission timeout, refusals inside admitted startup, and provider reporting. Other fence tests inject individual I/O failures on real disposable disk, not power loss, partial recursive removal, or every filesystem failure point.

Only pure identity/comparison/advance and reducers/delta functions execute in the explorer. Lease acquisition, disk/cache refresh, sticky runtime refusal, file publication/failure, and later attempts are modeled adapters. It does not execute Task/provider orchestration, API/UI message buffers, pending-tool-result clearing, nested arbitrary ancestry, protected action/question ownership, external syscall-time theft, process interruption, network/model behavior, or extension-host restart. Runtime tests and the parent verification own those boundaries. A green bounded result does not close #1469, enable B1/B2, or declare ordinary development globally stable.

## Provider handoff and scheduler model

`scripts/check-provider-handoff-scheduler.ts` is a separate bounded adapter model for the runtime boundary that the persisted lifecycle graph does not represent. Its breadth-first explorer normalizes provider-keyed records and owner arrays before deduplicating canonical states, then exhaustively explores enabled action orderings through depth 15 with a 20,000-state budget. It imports `selectHandoffExecutionContext` and the existing `delegateTaskToChild` and `completeDelegatedChild` reducers. A direct saved, unsaved, and locked-profile matrix checks task-local configuration selection within those cases. Stale provider lookup is caught before this pure selector, so focused provider tests check the failed lookup, contextual log, and fallback. The protocol state then models two provider instances, their claims and parent snapshots, authoritative parent/child records, current task publication, commit/start ownership, the child scheduler permit, queued and resumed parent state, and one bounded redelegation generation.

Provider locking, paused-child/current-task publication, and semaphore admission/release are explicit model abstractions rather than imported production code. Focused provider and `TaskScheduler` tests cover those concrete adapters. Lifecycle commits and completion use the real reducers. Parent publication and its queued continuation share an explicit transition owner: the fixed policy retains that ownership through matching resume invocation, then models the resumed run settling outside transition ownership. This permits a new delegation generation to begin while the prior resumed run remains active without allowing a stale continuation to start across the newer transition. The fixed policy checks every successor for continuous publication, one child start and commit per generation, exact commit-before-start ownership, permit release before parent resume or redelegation, matching parent transition/continuation ownership at resume invocation, and consistent final child/parent publication. It also requires both resume phases, every other action, and named semantic landmarks to remain reachable and fails if the depth boundary has an unseen successor.

Six injected legacy transition policies must produce deterministic shortest counterexamples through the same explorer: start before commit, resume before permit release, redelegation before permit release, empty current-task publication, two stale provider commits from competing snapshots, and releasing parent-transition serialization immediately after publication. The last witness must causally include first-child completion and parent publication, a second-child commit, release of the first child's scheduler permit, and then the stale first-child continuation. The checker prints the distinct reachable-state count, complete scenario/action/landmark coverage, bounds, and each named counterexample trace. It deliberately does not add a WAL, global profile projection, or scheduler state to persisted `HistoryItem` records.

For #921, the execution-context matrix checks saved, unsaved, and locked profile selection at the handoff boundary. For that bounded matrix, it establishes only that delegation writes the requested task-local mode and cloned configuration into the child context. It does not prove that every downstream consumer reads that context. The checker retains a divergent-mode witness in which the child task mode differs from the shared provider mode so reader refinements can demonstrate that choosing the wrong source is observable.

Merged PR #1625 changed the confirmed downstream readers: `getEnvironmentDetails` obtains `cline.getTaskMode()`, `presentAssistantMessage` passes that task-local mode to `validateToolUse`, and custom tool execution receives the same task-local mode. Focused production tests cover those three paths.

`scripts/check-delegated-mode-readers.ts` does not execute `getEnvironmentDetails`, `presentAssistantMessage`, or `validateToolUse`. It checks the production handoff selector and a pure built-in-mode permission divergence, establishing that the wrong source is observable. It is refinement support, not exhaustive reader coverage. Other mode-sensitive consumers remain an explicit inventory gap, and this suite does not claim universal task-local reader isolation.

## Task fan-out protocol model

`scripts/check-task-fanout-protocol.ts` is a separate, optional bounded protocol model for the #369/#372 fan-out safety contract. It explores a live parent with two sibling slots, a two-permit scheduler, independent result readiness, explicit child-to-parent delivery, parent loss, orphan cancellation, and permit release. It checks scheduler capacity and exact permit ownership, one writer and at-most-once delivery per child, readiness before delivery, and no result routing after parent loss. Named landmarks require concurrent siblings beneath a live parent, out-of-order result delivery, single-writer results, parent loss while work is running, and complete orphan cleanup to remain reachable. Injected unsafe states confirm those invariants reject wrong writers, early and duplicate delivery, post-parent-loss routing, and scheduler over-allocation.

This model checks an intended abstract composition boundary without claiming that concurrent sibling fan-out is enabled in production. It imports no production fan-out transition and is excluded from `pnpm lifecycle:model-check` and baseline CI. `TaskScheduler` provides generic bounded permits, but `ClineProvider` constructs it at the default capacity of one and production delegation persists a singular `awaitingChildId`. Raising production concurrency still requires live-parent result integration and extension-host coverage before fan-out can ship.

The production-backed lifecycle checker already models the current serial ownership invariant: a parent has at most one `awaitingChildId`, `delegatedToId` matches it, and every active/delegated linked child is the child currently awaited. The reducer rejects re-delegation while that child is active. This is exhaustive only for the checker's three slots and depth 12 and does not erase the documented cross-host stale-write violations, so baseline closure still requires their production fixes and model promotion.

## Completion persistence model

`scripts/check-completion-persistence.ts` models the completion-readiness protocol that protects the public `TaskCompleted` event. It starts from both standalone and delegated tasks and exhaustively interleaves:

- starting, finishing, or failing the assistant-history write;
- accepting completion before, during, or after persistence;
- scheduling a bounded retry, completing its delay, and starting the retry write;
- exhausting retries;
- cancellation or disposal at every reachable non-completed state;
- delegated parent reopen success or failure after durable child history; and
- emitting completion.

The model abstracts restart visibility as the `durable` history phase. It allows an already-started write to finish after cancellation because the filesystem operation itself is not cancellable, but it forbids starting a retry write or emitting completion after cancellation. The retry bound is two write starts (the initial attempt plus one retry), which is sufficient to cover the ordering and cancellation state classes without mirroring the production retry count.

Seven semantic landmarks keep the intended positive and negative paths reachable: delayed completion remains pending, failed completion remains pending, exhausted retries settle without completion, cancellation can win after retry delay but before persistence, delegated reopen failure emits no delegated completion, and both standalone and delegated tasks can complete after durable history. The checker explores all reachable states through depth 10 and fails rather than reporting a truncated pass if an unseen successor remains.

## Invariants

The task delegation checker currently enforces:

1. A delegated parent has exactly one `awaitingChildId`, and `delegatedToId` matches it.
2. The awaited child exists, links back to the parent, is not completed, and remains in `childIds`. A delegated child may itself await a nested child.
3. Non-delegated parents retain no active delegation pointer.
4. Every active or delegated linked child is the child its parent currently awaits. An interrupted prior child may retain lineage after re-delegation but cannot complete back into that parent.
5. Parent-child lineage is acyclic.
6. Completed task records cannot be changed by later lifecycle events.
7. Active-child re-delegation, stale completion after ownership moves to another child, duplicate/late completion, and abandonment of a live child are rejected by the shared production guards.

The completion persistence checker additionally enforces:

1. `TaskCompleted` requires accepted completion and restart-visible assistant history.
2. Delayed, failed, and retry-exhausted persistence cannot emit completion.
3. Cancellation or disposal settles the modeled readiness wait, clears pending retry state, starts no later retry write, and emits no completion.
4. Delegated completion crosses the same durability boundary as standalone completion and requires successful parent reopen.
5. A failed delegated parent reopen cannot emit the delegated completion event.

These are safety claims within the documented bounds. The checks do not claim liveness, fairness, power-loss durability, filesystem-lock correctness, or exhaustive coverage of arbitrary task counts or retry counts. The completion explorer specifies the event contract rather than importing `Task` or `AttemptCompletionTool`; focused unit tests and the restart E2E verify that concrete production paths implement the modeled guards. Delegated reopen is abstracted as one success-or-failure event after durable child history; fallback from a failed reopen into the normal standalone completion flow remains production-test coverage rather than part of this model. The lifecycle checker also does not distinguish a delayed pre-interruption completion from a legitimate post-resume completion for the same child ID; that requires a persisted attempt/generation token before it can become a sound invariant.

## Extending the model

When production lifecycle behavior changes:

1. Define or update the pure transition in `taskLifecycle.ts`, then call it from the production operation.
2. Model the corresponding enabled event in `scripts/check-task-lifecycle.ts`.
3. Encode an invariant for the bug class, or a representative rejected-event scenario when the event intentionally leaves state unchanged.
4. Increase depth or task slots only when the new scenario requires it. Keep the state budget explicit and ensure CI completes quickly.
5. Convert any discovered counterexample into a focused production regression test as well as retaining the architectural invariant.

Completion-readiness changes belong in `scripts/check-completion-persistence.ts`; shared-store interleavings belong in `scripts/check-task-store-concurrency.ts`. Optional fan-out work belongs in `scripts/check-task-fanout-protocol.ts` and its separately scoped ticket until production transitions exist. Do not weaken bounds or remove an invariant merely to make CI pass. If state growth becomes difficult to control, split independent protocols or move the model to TLC/Quint with an implementation trace adapter rather than silently sampling the state space.

Parser request scoping is one such independent bounded submodel within the umbrella suite. Extend `scripts/check-native-tool-call-parser-scoping.ts` and its focused architecture document instead of adding parser state or transitions to `taskLifecycle.ts` or the persisted lifecycle state graph.

## Pending-question barrier

The umbrella also runs `scripts/check-pending-question.ts`, a separate bounded check using the production question reducers. It checks identity ownership, interruption retention, rejection of stale and duplicate answers, explicit empty/image answers, durable-result clearing, and explicit abandonment/replacement. Limits are depth 8 and 100 distinct states. This does not prove request-stream, webview, filesystem, or extension-host behavior; focused runtime tests exercise those internal boundaries separately.

Question metadata is owned by `TaskHistoryStore.updateQuestion`, which executes its reducer against the current disk record inside the atomic writer's file lock. Generic request interruption does not clear it. Only an owned explicit answer or configured owned auto-answer can populate its answer field. The native result is written before clearing the record; historical unanswered UI rows do not create pending runtime state.

## Ordinary runtime refinement — ZOO-ORDINARY-DELEGATION-20261008

The [phase repair](../implementation/ordinary-delegation-20261008-phase-evidence.md:52), [provider repair](../implementation/ordinary-delegation-20261008-provider-evidence.md:42), and [prepared continuation repair](../implementation/ordinary-delegation-20261008-continuation-evidence.md:17) add actual scheduler/constructed-Task/presenter/provider/disposable-store coverage for boundaries the abstract models do not execute. Arbitrary supplied callbacks retain capable ownership and protected idle-wait refusal.

The [current completion regression](../../src/core/webview/__tests__/ordinaryCompletionOwnership.spec.ts:1) reproduced transcript publication against a newer native delegation call before eventual ownership-moved refusal. The bounded repair acquires cooperative parent/child ancestry ownership before admission and transcript effects, retaining it through final parent publication. It proves finite participating-provider/store schedules, exact result correlation, stale replay refusal and truthful committed prefixes, not universal issue closure.
