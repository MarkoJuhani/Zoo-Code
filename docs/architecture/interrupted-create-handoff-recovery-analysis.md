## Required invariants and eligibility predicate

The only trigger is **sending a new message to this existing chat** (direct or already queued), never Continue. Normal question IDs, answer ownership, follow-up responses, question queue/drain and all ordinary asks must keep their current semantics; pending-question ownership takes precedence. Define a dedicated recovery discriminator, not a generic `resume_task`/`messageResponse` shortcut. Nothing may launch a child, delete a child/task directory, fabricate success, or blanket-clear pending actions.

At recovery, and again immediately before each mutation under a cross-host coordination mechanism, require ALL: (a) authoritative current parent ID and root/parent lineage match the targeted conversation; (b) parent status is `interrupted`, no pending question, no awaited/delegated child for this action, and no conflicting live owner; (c) pending action is **exactly** `create_subtask` with the expected action ID, not a superseding action; (d) exactly one matching unfinished assistant `new_task` tool use at the effective API boundary, no other unresolved tool use or matching success/error result; (e) no committed child linked to this action in parent child IDs, child metadata, root lineage, other provider/task registries or persisted handoff intent; (f) each transient directory is attributed by timestamp, parent/root metadata and handoff intent where present, and absence of metadata is not treated as positive proof of no child. If any reader is missing/invalid, status changed, other host is delegating, or provenance is ambiguous, stop, retain the pending action and message, and report a non-sensitive reason. Only an authoritative persisted matching error result may qualify for idempotent retry after a partial write.

## Proposed recovery protocol (design to validate; not implemented)

Use a **per-parent cross-process recovery/handoff mutex** respected by every writer capable of launching or committing this action, including the provider, recovery, and startup reconciliation. Specify lock order with existing per-file locks and timeout/stale-lock behavior; never hold a file lock while attempting to acquire the outer lock. Merely locking the three files in sequence is insufficient when a competing writer does not honor the same fence. A durable, versioned intent/journal keyed by `(parentId, actionId, messageId)` provides a recoverable state machine; file writes can remain independent because retry is idempotent. Prove how the scheme fences a second extension host and how peer writers are detected. If existing providers cannot participate in the fence, fail closed rather than claim cross-host correctness.

1. **Intake before UI acknowledgment:** assign a stable message ID at the webview boundary and durably journal the text/images or securely referenced attachments with the parent ID and action ID. Read it back, then acknowledge the UI submission; only then may the UI clear its input. For an already queued in-memory item, durably adopt its ID/payload before claiming it for recovery. A UI feedback row is a view, not the source of truth. On failed intake, keep the input/queue item and show a scoped failure state; avoid payloads and image data in logs. Define attachment lifetime, storage protection and retention/cleanup policy.
2. **Eligibility under fence:** inspect fresh authoritative parent, root, all linked children/intent, API boundary, and journal. Freeze the exact action/message and reject changed versions. Distinguish an existing matching **non-success** result from conflicting or successful results. Never silently repurpose a result for a different message.
3. **API commit:** append one user turn containing a `tool_result` with `tool_use_id` equal to the pending `new_task` action ID, `is_error: true`, and precise non-success content. Associate the stable message ID and user's message (and attachments) in a durable delivery record / same recoverable turn; do not send the message again as an independent turn on retry. Compare-and-append under the API file lock, checking the exact terminal call and absence of a result **inside** that lock; read back the expected result and message association. A stale snapshot merge that merely preserves both turns is not compare-and-append. Decide whether the existing request loop must start with empty content or skip its append when the user turn was committed; test the provider's effective-history and tool-result formatting rules.
4. **Metadata repair:** under the outer fence and authoritative task-file compare-and-swap, require the same action ID and an already verified durable error result, no awaited/committed child or new owner, then clear **only that pending action**. If a runnable `active` parent is necessary, implement one named, audited administrative repair for this exact terminal error-result shape, not a general lifecycle transition or status overwrite. Preserve historical child IDs and completed-child summary. Read back status/action after writing; ensure startup reconciliation and normal history saves cannot revert it. If the lifecycle cannot support this repair safely, stop with the journal intact.
5. **Delivery/acknowledgment:** rehydrate API history and the journal, start the same chat's request loop once using the persisted user turn; define and persist a delivery marker at a concrete boundary (e.g., durably appended user turn and recoverable scheduled-loop intent), and on restart resume without appending/sending it twice. A request-loop _start attempt_ alone is not durable evidence of delivery. Acknowledge/remove the claimed queue item only after its stable ID is durably represented in the API/delivery state and rehydration can resume that state. It may remain visible as pending until then. The journal must support retry when the host dies between acceptance, API result, metadata update, loop scheduling, and request start.

## Crash/retry table and acceptance tests

- Intake fails: input/queue stays recoverable; no UI success acknowledgment, no API or metadata change. Intake succeeds then reload: journal rehydrates the item and recovery remains eligible.
- UI feedback save fails: journal remains authoritative; no queue acknowledgment. UI feedback succeeds but API append fails: journal survives; retry cannot duplicate feedback or lose the message. API write returns failure after disk commit: read back and recognize the same result/message ID, not append a second result.
- API result succeeds but metadata update fails: on reopen recognize exactly one matching error result, retain journal and pending metadata, retry the guarded metadata repair, never replay delegation. Metadata repair succeeds but loop fails/reloads: rehydrate the durable turn and scheduled work, never repeat the user turn or discard the item prematurely.
- Concurrent host appends a result, changes action/status or commits a child: fence/CAS rejects stale recovery; preserve the child's ownership and message; no synthetic success or child deletion. A transient uncommitted child alone does not certify successful delegation; ambiguous provenance blocks recovery.
- Explicit Continue during recovery cannot resolve the handoff or silently consume its ask; a later message (direct or queued before/after ask, including images) is accepted once. Existing pending-question waits, question ID ownership, follow-ups, ordinary asks and unrelated queues remain unchanged.
- Isolated fault-injection tests must cover opening, immediate and late queue arrival, restart at **every** durable stage, mismatched/superseded action ID, extra/missing tool calls, existing error/success result, committed versus transient child, failed UI/API/metadata/journal writes and read-back, two competing hosts, no child launch, no lost/duplicate user message and lifecycle-compliant status. Avoid live Odoo tests or actual subtask invocation.
