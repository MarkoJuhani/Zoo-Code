2. Missing/unreadable reader, unexplained missing record, contradictory attribution or uncovered registry is unknown, not negative. The readers below are candidates, **not** demonstrated complete coverage. 3. Only then manually send a NEW DIRECT message to the interrupted parent. Before NEW direct recovery intake and again at guarded mutation, check for a surviving same-parent/same-action queued request (including one whose action attribution cannot be ruled out): defer only this recovery until the user resolves it via ordinary queue controls; retain direct input and queue ownership, without claiming/removing or assuming survival of the pre-stop item. ## Wire discriminator and immutable identity

- Only a manually sent **fresh DIRECT message to the existing interrupted parent chat**, after manually stopping the development queue and host and restarting a verified loaded build, may enter `interrupted_create_subtask_recovery_v1`. An old queued item is not a recovery trigger; do not claim it survived, adopt/claim/remove it, or promise in-memory queue restoration. Ordinary `resume_task`, normal `askResponse`, `queueMessage`, pending-question answers, follow-ups and unrelated queues/parents/children keep their existing routes and behavior. A pending question takes precedence with exact question ID/answer ownership; Continue does not consume the recovery waiter. Failed eligibility or same-action queue deferral leaves direct input intact and reports a redacted reason; no child is launched.
- Webview assigns a cryptographically random stable `submissionId` before posting each NEW direct recovery submission (text, image-only or mixed); retries/reloads of that same submission keep its immutable exact payload, ID and timestamp. Do not regenerate an ID or bind another payload to a recorded result. Scope identity to `(parentTaskId, actionId, submissionId)` plus `rootTaskId`, parent lineage and exact action generation; reject digest/payload mismatch or ID collision across bindings. Only one accepted submission can resolve an action; later messages take normal routes. Preexisting queued entries remain under ordinary queue ownership, without recovery claim or silent removal. If an identical ID was ALREADY durably accepted, reconcile/replay its existing receipt and progress rather than accepting or appending a duplicate; an unproven old in-memory item is never treated as durable.
- Reconcile a missing receipt for a NEW direct submission from persisted state on reload; emit typed receipt `{submissionId,parentTaskId,actionId,payloadDigest,acceptedVersion}` only after durable write AND authoritative read-back of text/attachment references. Receipt acknowledges intake, not API or remote delivery. If acceptance fails, UI retains the exact direct draft/images; no success feedback or implicit queue mutation. UI clears only the exact unchanged direct submission after matching receipt, never a newer edit. Already-cleared legacy input and the pre-stop queued item have no guaranteed recovery.
- **Binding issuance:** Under verified exceptional-recovery host/root authority and fresh authoritative lineage/action read, issue and durably record one immutable positive integer `actionGeneration` for this action incarnation before NEW direct intake. Return it on repeat only for identical persisted action ID/kind, parent/root lineage and fingerprint; missing or changed evidence blocks. This is an action identity, **not** a host/lease epoch. A new incarnation, even with a reused action ID, needs a different generation or blocks. Webview cannot invent it. Direct retry keeps its random `submissionId` and exact payload; unavailable binding retains input. P2 owns issuance, P3 owns direct UI handshake; current helpers are unwired. No queued-adoption handshake is required for this selected scope.
- **Receipt replay is not new intake:** Before classifying any NEW direct recovery intake, look up the exact `(parentTaskId,actionId,submissionId)` in the immutable accepted projection retained through later states and action clear. Under verified exceptional-recovery authority freshly check schema, digest, protected payload bytes, original root/lineage/action binding and later API/result/metadata correlation. Return original receipt and `acceptedVersion` only for identical immutable ID/binding/digest/payload, including an accepted identical ID previously submitted before a restart. Conflict or missing proof blocks without acknowledgment/history change. A repaired task is not judged by the initial interrupted predicate for replay; replay cannot claim a queued item, accept a new owner, append a turn or start a loop. Pending direct UI snapshot persists until matching receipt; P3 scaffold currently classifies before replay and must change before wiring.

## Versioned durable record, privacy and state machine

- Store a per-parent versioned recovery journal in protected parent task storage, never in UI feedback or the in-memory queue. Unique identity `(parentTaskId,actionId,submissionId)` includes root/lineage, immutable action generation, payload digest/length/reference and correlation to API `messageId`/assistant call/result; mutable progress includes revision, scheduling intent, local acknowledgment and external-send uncertainty. No cross-host `fenceGeneration`, `ownerToken`, lease renewal or automatic migration is required for this manually stopped exceptional recovery. **New journal schemaVersion=2**; candidate schemaVersion=1 scaffold/legacy record is NOT silently compatible and must be rejected until explicitly reviewed and tested migration exists. Unknown/missing/corrupt version, payload/blob or conflicting action blocks. Persisting an old error alone never invents a journal.
- **Canonical submission identity (unchanged v1 preimage):** Retain `actionGeneration`, ordered parent-chain snapshot and lowercase SHA-256 `payloadDigest` over fixed-order UTF-8 JSON `{binding:{parentTaskId,rootTaskId,parentLineage,actionId,actionGeneration},submissionId,origin,timestamp,payload:{text,images}}`; images are ordered, exact canonical `data:image/{png|jpeg|gif|webp};base64,` strings, without skip, truncate, reorder or deduplication. Identity digest is not secrecy. Resolve all attachments to exact validated bytes/MIME/canonical base64 before hashing, persistence or receipt; any unreadable, unsupported or shortened source rejects the entire submission and retains input. Persist text and ordered decoded image bytes in protected immutable blobs with MIME, length and SHA-256; read-back reconstructs and verifies the canonical preimage. The new journal is `schemaVersion=2` with monotone `revision` starting at 1, while immutable receipt `acceptedVersion=1` is unchanged across later journal states. No inline image data URI is durable storage. Existing P3 schemaVersion=1 fixture/projection needs explicit v2 adapter change and tests before wiring; do not silently reinterpret it.
- Protected storage retains UTF-8 text and image bytes in immutable blobs in the same canonical task root (directory 0700, file 0600, atomic write + file sync + rename + directory sync where supported). Journal stores relative safe references and digests, not data URIs or plaintext logs; reject unsafe path/symlink/permission or filesystem semantics. OS protection is not encryption: a policy requiring encryption blocks intake until separately approved. Read-back verifies exact bytes/digests. Keep bounds of <=1 MiB UTF-8 text, <=8 MiB decoded images, <=10 images and <=16 MiB encoded request; oversize fails without clearing input. Do not log payload, tokens, paths, raw errors or content hashes; report short non-secret reason/correlation. Rehydrate from durable blob, never transient URI. P3 must prove resolver source lifetime through acceptance and restart. **No automatic blob/journal cleanup in this release**: retain until existing separately approved explicit task deletion; storage-growth/retention policy must be reviewed before enabling production intake. Never delete pending/uncertain records automatically.
- Minimum persistent progress is `accepted` -> `api_committed` -> `metadata_repaired` -> `scheduled` -> `locally_acknowledged`, with `external_send_uncertain` when dispatch starts without reliable acknowledgment. These are crash-reconciliation checkpoints, not five services/files; one schemaVersion=2 journal with revision and fresh authoritative reads suffices. NEW direct intake requires durable payload/journal read-back before receipt; API commit requires one correlated error+user turn; guarded action/status repair requires read-back; scheduling requires resumable intent; local acknowledgment requires a durable marker. No queue removal follows acknowledgment in this scope. Identical retries are no-ops; gaps/conflicts reconcile from files without skipping a stage. Roll forward after partial commit, never relaunch a child to undo API error. Preserve original action until verified repair and history throughout. No automatic cleanup or 30-day timer; retention until separately authorized explicit task deletion with future reviewed reader/lifetime policy.
